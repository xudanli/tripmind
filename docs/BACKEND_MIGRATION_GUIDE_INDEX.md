# 后端迁移实施指南 - 总索引

## 📋 概述

本文档是后端迁移实施指南的总索引，包含所有高优先级迁移任务的详细实施文档。

---

## 🎯 迁移目标

将所有应该在后端处理的业务逻辑从前端迁移到后端，包括：
1. 数据格式验证和修复
2. 总费用计算
3. 数据转换逻辑统一
4. 货币推断和格式化

### [第二部分：总费用计算](./BACKEND_MIGRATION_GUIDE_PART2.md) ✅ **已完成**

**目标：** 后端自动计算行程总费用，前端无需计算

**实施状态：** ✅ **已完成**

**已实现内容：**
- ✅ 创建了 `CostCalculator` 工具类（`src/utils/costCalculator.ts`）
- ✅ 在生成行程时自动计算总费用（`validateAndTransformResponse()`）
- ✅ 在创建行程时自动计算总费用（`createItinerary()`, `createItineraryFromFrontendData()`）
- ✅ 在更新行程时自动重新计算总费用（`updateItineraryFromFrontendData()`）
- ✅ 在创建活动时自动重新计算总费用（`createJourneyDayActivity()`）
- ✅ 在更新活动时自动重新计算总费用（`updateJourneyDayActivity()`）
- ✅ 在删除活动时自动重新计算总费用（`deleteJourneyDayActivity()`）
- ✅ 创建了重新计算总费用的接口（`POST /api/v1/journeys/:journeyId/recalculate-cost`）

**效果：**
- ✅ 所有关键操作都会自动计算或重新计算总费用
- ✅ 前端可以直接使用后端返回的 `totalCost`，无需计算
- ✅ 总费用始终准确，反映当前活动列表的费用总和

### [第三部分：数据转换逻辑统一](./BACKEND_MIGRATION_GUIDE_PART3.md) ✅ **已完成**

**目标：** 统一前后端数据格式，减少前端的数据转换工作

**实施状态：** ✅ **已完成**

**已实现内容：**
- ✅ 改进了 `convertActivitiesToTimeSlots()` 方法
  - 使用 `DataValidator` 修复所有字段
  - 统一字段映射：`location` → `coordinates`
  - 统一字段映射：`title` → `activity`
  - 构建 `details` 对象
- ✅ 创建了统一的前端格式 DTO
  - `ItineraryDetailWithTimeSlotsDto` - 行程详情 DTO（使用 timeSlots）
  - `ItineraryDayWithTimeSlotsDto` - 天数 DTO（使用 timeSlots）
- ✅ 创建了实体转前端格式的方法
  - `entityToDetailWithTimeSlotsDto()` - 将实体转换为前端格式
- ✅ 更新了主要接口返回前端格式
  - `getItineraryById()` - 获取行程详情
  - `createItinerary()` - 创建行程
  - `updateItineraryFromFrontendData()` - 更新行程

**效果：**
- ✅ 后端直接返回前端期望的格式（使用 timeSlots 而不是 activities）
- ✅ 统一字段命名（使用 coordinates 而不是 location）
- ✅ 自动处理字段映射和 details 对象构建
- ✅ 前端可以直接使用后端返回的数据，无需进行数据转换

## 🚀 实施顺序建议

### 阶段一：基础功能（1-2周）

1. **第一部分：数据格式验证和修复**
   - 优先级：最高
   - 影响：所有API响应
   - 风险：低

2. **第二部分：总费用计算**
   - 优先级：高
   - 影响：行程生成和更新
   - 风险：中

### 阶段二：数据统一（1-2周）

3. **第三部分：数据转换逻辑统一**
   - 优先级：高
   - 影响：所有行程相关接口
   - 风险：中（需要数据迁移）

### 阶段三：增强功能（1周）

4. **第四部分：货币推断和格式化**
   - 优先级：中
   - 影响：行程生成和货币显示
   - 风险：低

## 🔍 测试策略

### 单元测试
- 每个工具类都应该有完整的单元测试
- 测试覆盖率应该达到80%以上

### 集成测试
- 测试完整的API流程
- 验证数据格式正确性
- 验证计算逻辑正确性

### 回归测试
- 确保现有功能不受影响
- 验证前端可以正常使用新格式的数据

## 📝 注意事项

1. **向后兼容**
   - 在过渡期间，可以同时支持新旧格式
   - 前端可以检查字段存在性，优先使用新格式

2. **数据迁移**
   - 对于现有数据，需要运行迁移脚本
   - 确保数据迁移不会丢失信息

3. **性能考虑**
   - 数据验证不应该影响性能
   - 费用计算可以考虑缓存
   - 货币推断可以使用缓存

4. **错误处理**
   - 所有验证失败都应该有明确的错误信息
   - 记录所有数据修复操作，便于排查问题
